# Hasad Views

يسحب منشورات قناة `@hasadalyoum` ويرسل طلب مشاهدة لكل رابط جديد مرة واحدة عبر GitHub Actions وPlaywright. يتولى Supabase تشغيل الـworkflow دوريًا.

## الإعداد
أضف أسرار الحسابات الثلاثة من Settings > Secrets and variables > Actions:
- الحساب 1: `SITE_USERNAME_1` و`SITE_PASSWORD_1`
- الحساب 2: `SITE_USERNAME_2` و`SITE_PASSWORD_2`
- الحساب 3: `SITE_USERNAME_3` و`SITE_PASSWORD_3`

يمكن تشغيل workflow يدويًا من Actions > Hasad Views > Run workflow. إعادة محاولة رابط يدويًا متاحة من workflow مستقل، ولا تدخل ضمن التشغيل المجدول.

## آلية التشغيل
- يستدعي Supabase workflow الرئيسي في GitHub Actions كل 30 دقيقة.
- يبدأ جمع الروابط بعد `https://t.me/hasadalyoum/26732`؛ أي أن الرابط 26732 وما قبله مستبعد.
- يعالج كل تشغيل الروابط الجديدة التي لم تُسجل سابقًا فقط، مرتبة من أحدث رقم منشور إلى أقدم رقم في الدفعة.
- إذا لم تظهر روابط جديدة، ينتهي التشغيل دون إرسال طلبات مشاهدة ودون إعادة معالجة روابط سابقة.
- لكل رابط جديد محاولة واحدة؛ ولا يعاد الرابط تلقائيًا إذا فشلت المحاولة. التشغيل التالي يلتقط المنشورات الأحدث فقط.
- تُحفظ الروابط التي اكتُشفت سابقًا في `state/processed_links.txt`، وتُحفظ روابط دفعة التشغيل في `state/telegram_links.txt` أثناء العمل.
- يستخدم كل تشغيل حسابًا واحدًا بالتناوب بين الحسابات الثلاثة. يحفظ مؤشر الحساب في `state/account_rotation.json`، ولا تُحفظ بيانات الدخول في ملفات الحالة.
- يتطلب الاستدعاء المجدول أن يكون سر GitHub ذو صلاحية تشغيل workflow محفوظًا في Supabase Vault باسم `github_actions_token`.

## تصفير الحالة
لا تُحذف ملفات الحالة إلا عند الرغبة في إعادة اكتشاف الروابط عمدًا. إبقاء `processed_links.txt` يمنع تكرار معالجة المنشورات.
